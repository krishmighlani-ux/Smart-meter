# ⚡ AI-Powered Smart Meter of the Future

**Team:** Krish Mighlani · Shauryajeet Mahapatra · Ayush Rana

An electricity-monitoring web application that combines **IoT concepts** (a documented device-ingestion API for an ESP32), **cloud-style architecture** (Next.js API + MongoDB + a separate ML service) and **machine learning** (consumption forecasting and anomaly detection).

> **Important – data is simulated.** No real meter or sensor is connected. All readings are generated by a seeded simulator and every screen says so. The ingestion API exists so real ESP32 readings can be added later; it has not been tested with real hardware.

## Features

| # | Feature | Where |
|---|---|---|
| 1 | Dashboard: latest power, today's kWh, estimated monthly bill (₹), 7-day peak, 24 h trend | `/` |
| 2 | Daily / weekly / monthly interactive charts | `/analytics` |
| 3 | Next-24 h forecast (Gradient Boosting) with MAE / RMSE / MAPE / R² vs a naive baseline | `/forecast` |
| 4 | Anomaly detection (Isolation Forest) – explained as a *warning, not proof of theft* | `/alerts` |
| 5 | Savings recommendations from usage + **configurable tariff** | `/savings` |
| 6 | Alerts with timestamp, severity and explanation | `/alerts`, dashboard |
| 7 | Meter list, details and paginated historical readings | `/meters` |
| 8 | Responsive layout (desktop sidebar, mobile tab bar) | all pages |

## Quick start (about 5 minutes, no database needed)

Requirements: **Node.js 20+**, **Python 3.10+**.

**Terminal 1 – ML service**
```bash
cd ml
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m smartmeter_ml.service                         # http://127.0.0.1:8001
```

**Terminal 2 – web app**
```bash
cd web
cp .env.example .env.local        # leave MONGODB_URI empty for demo mode
npm install
npm run dev                        # http://localhost:3000
```

Open http://localhost:3000. With `MONGODB_URI` empty, the app generates 90 days of **simulated** hourly data for two meters in memory at start-up (data is lost on restart).

### With MongoDB
1. Create a free cluster on [MongoDB Atlas](https://www.mongodb.com/atlas) (or run local MongoDB) and copy the connection string.
2. Put it in `web/.env.local`: `MONGODB_URI=mongodb+srv://user:pass@cluster/...` (optional `MONGODB_DB=smartmeter`).
3. `cd web && npm run seed` – creates indexes, 2 simulated meters, 90 days of readings and default tariffs (safe to re-run).
4. `npm run dev`.

### Environment variables (`web/.env.example`)
| Variable | Purpose |
|---|---|
| `MONGODB_URI`, `MONGODB_DB` | Database. Empty URI = in-memory simulated demo data |
| `ML_SERVICE_URL` | Where the Python service runs (default `http://127.0.0.1:8001`) |
| `ML_SERVICE_TOKEN` | Optional shared secret; set the same value for the ML service (env var) and the web app |
| `INGEST_API_KEY` | Required to enable `POST /api/readings`. Generate a long random string. Never commit it. |

## Database schema (MongoDB, database `smartmeter`)

**`meters`** – one document per meter (unique index `meterId`)
| Field | Type | Notes |
|---|---|---|
| `meterId` | string | e.g. `SM-HOME-001` (`[A-Za-z0-9_-]{3,40}`) |
| `name`, `type`, `location`, `phase` | string | descriptive |
| `sampleIntervalMin` | number | 60 in this prototype |
| `source` | `"simulated"` \| `"device"` | drives the banner shown in the UI |
| `status`, `installedAt` | string, date | |

**`readings`** – one document per meter per hour (unique compound index `{meterId, ts}`)
| Field | Type | Notes |
|---|---|---|
| `meterId` | string | references `meters.meterId` |
| `ts` | Date (UTC) | hour-aligned |
| `powerKw` | number | average power in the interval |
| `energyKwh` | number | `powerKw × interval hours` |
| `voltageV`, `currentA` | number, optional | |
| `source` | `"simulated"` \| `"device"` | |

**`tariffs`** – one per meter (unique index `meterId`): `offPeakRate`, `peakRate` (₹/kWh), `peakStartHour`, `peakEndHour` (IST, 0–23, may wrap midnight), `fixedMonthlyCharge` (₹), `updatedAt`.

Alerts are **computed on demand** from readings by the ML service; they are not stored.

## API reference (all JSON; errors are `{ "error": "message" }`)

| Method & path | Description |
|---|---|
| `GET /api/health` | Status and data mode |
| `GET /api/meters` | List meters with latest reading |
| `GET /api/meters/:meterId` | Meter details, tariff, reading count |
| `GET /api/summary?meterId=` | Dashboard figures + 24 h trend |
| `GET /api/analytics?meterId=&range=daily\|weekly\|monthly` | Bucketed kWh (buckets with missing hours are flagged `partial`) |
| `GET /api/readings?meterId=&date=YYYY-MM-DD&page=&pageSize=` | Historical readings for one IST day |
| `POST /api/readings` | **Ingest** readings. Header `x-api-key`. Body: `{ "meterId", "readings": [{ "ts": ISO-8601, "powerKw", "voltageV?", "currentA?" }] }` (max 500) |
| `GET /api/forecast?meterId=&horizon=1..24` | Forecast + evaluation metrics (needs ML service) |
| `GET /api/alerts?meterId=` | Anomalies, severity, explanations (needs ML service) |
| `GET /api/recommendations?meterId=` | Savings suggestions using the saved tariff |
| `GET /api/tariff?meterId=` · `PUT /api/tariff` | Read / update tariff. Body: `{ "meterId", "tariff": {...} }` |

`meterId` defaults to the first meter. Inputs are validated with zod; bad input returns `400`, unknown meter `404`, bad/missing API key `401`, ML service down `503`, unexpected errors a generic `500` (details only in server logs).

ML service (internal): `POST /forecast`, `POST /anomalies`, `GET /anomalies/self-check`, `GET /health`.

## How the ML works
* **Forecast** (`ml/smartmeter_ml/forecast.py`): `GradientBoostingRegressor` on features available at forecast time – hour (sin/cos), weekday, weekend flag, value 24 h ago, 168 h ago, and the mean of the same hour over the last 7 days. No future data leaks into training. It is evaluated on a **chronological hold-out (last 7 days)** and compared with a seasonal-naive baseline (same hour yesterday). Metrics shown in the UI are computed live from that hold-out – nothing is hard-coded.
* **Anomaly detection** (`anomaly.py`): `IsolationForest` over power, deviation from the median for that hour of day, and hour encoding. Flags are kept only if the reading is ≥50 % away from the usual value for that hour. Severity comes from that ratio. **An anomaly is a warning, not proof of electricity theft** – it can be a heavy appliance, a new load or a faulty reading. Hours filled in by gap interpolation are never flagged.
* **Data gaps:** gaps ≤ 24 h are linearly interpolated; after a longer gap only the latest contiguous run is used.
* Because the demo data is simulated, accuracy figures describe the simulator, **not real homes**. The "self-check" on the Alerts page measures detection on synthetic spikes whose positions are known, which is an easy case.

## Deployment (not tested by the authors – follow and adjust)
* **Database:** MongoDB Atlas free tier; allow your hosts' IPs in Network Access.
* **ML service:** any Python host (Render, Railway, a VM). Start command: `gunicorn -w 2 -b 0.0.0.0:$PORT smartmeter_ml.service:app`. Set `ML_SERVICE_TOKEN`.
* **Web app:** Vercel (root directory `web`). Set `MONGODB_URI`, `ML_SERVICE_URL` (public URL of the ML service), `ML_SERVICE_TOKEN`, `INGEST_API_KEY`. Run `npm run seed` once from your laptop against Atlas.
* Without a hosted ML service, forecast and alerts will show a clear "ML service unreachable" error while the other pages keep working.

## Connecting real hardware later
1. Measure with an **ESP32** plus a sensor such as a PZEM-004T v3 (voltage/current/power over UART), or SCT-013 (current) + ZMPT101B (voltage). Mains wiring is dangerous – use certified, isolated modules and get supervision.
2. Create a meter document with `source: "device"`.
3. Have the ESP32 send hour-aligned UTC readings with `POST /api/readings` and the `x-api-key` header (see `hardware/esp32_example.ino`, **untested**).
4. The UI banner switches from "Simulated data" to "Readings from a connected device" for meters whose `source` is `device`.

## Known limitations
* Simulated data only; no real sensor testing.
* Two-rate tariff only; real utility slabs, taxes and surcharges are not modelled.
* The MongoDB code path and the deployment steps have not been run against a live MongoDB/Vercel by the authors' tooling; run `npm run seed` and check `/api/health` shows `"database":"mongodb"`.
* In-memory demo mode loses ingested data on restart.
* The API has no user authentication (only the ingest key); do not expose it publicly with real customer data.
* The ML service retrains on each new data snapshot (results are cached per snapshot); fine for a prototype, not for many meters.
